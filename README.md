## Pipeline explanation
### Raw sequence trimming and quality filtering
1.  Kneaddata is first used to perform some basic quality control on the input sequences. It takes the paired read files as provided by the sequencing company and, through tools such as trimmomatic, bowtie2, fastqc and trf removes their primers, removes overrepresented sequences, tandem repeats, reads which do not have enough quality using a sliding window and reads which are flagged as belonging to a contaminants database. It outputs eight fastq.gz files, depending on how it has flagged the reads within. I only use the reads which have passed the filtering and quality filtering step going forward, whether they are paired or unpaired.
2.  (optional) In a few occasions, kneaddata does not work properly and generates paired files which have an unequal number of reads in them. In those few cases I ran fastq_pair on them manually. fastq_pair takes in two supposedly paired end files and separates the reads of the files which match from those that do not match (e.g., if the fw file had 1004 reads and the rv file had 1000 reads, it would generate three files: a new fw file with the 1000 matching reads, a ne-named rv file with its original 1000 reads and a new fw-unpaired reads file with the unmatched 4.). I would later concatenate the newly generated unmatched files with their corresponding, original unmatched reads files (following the last example, the newly generated fw-unpaired file with 4 reads would be concatenated using cat with the fw unmatched reads file originally produced by kneaddata)
### Generating scaffolds and mapping the reads to said scaffolds
3.  The SPAdes assembler pipeline, in metagenomes mode (metaSPAdes), is used to generate scaffolds from the quality filtered, trimmed reads. For a given sample, both the paired forward and reverse reads and their corresponding unpaired reads are used as input, and the resulting scaffolds.fasta (which get renamed to include the sample name following the format SXX_scaffolds.fast, XX being the sample name) is used in all steps going forward
4.  Bowtie2 and Samtools are used to generate an index from the contigs, a map of the reads to the contigs (in .sam format) and then convert said map to .bam, sort it and generate its index (in .bai format). So, it takes the SXX_scaffolds.fasta file from the last step as input and generates a SXX_map.sam, a SXX_map.bam, a SXX_map_sorted.bam and a SXX_map_sorted.bai file as its output (the .bai format is generated as a byproduct, as samtools index is a destructive process that modifies the original file without generating a copy. For that reason, the SXX_map_sorted.bam file is used as the sorted and indexed file going forwards)
### Binning the contigs using different binning tools
I opted for running various binning tools instead of a single one and then comparing and polishing their results using a bin refinement tool, as while various benchmarks exist that compare different binning tools in different scenarios, there is not a single tool that is widely recognized as the most appropriate one that should be used above the rest. 
The choice of binning tools was based on (1) their usage on literature and works similar to this one, (2) the clarity of their associated documentation (as I didn't want to implement tools I wasn't able to grasp their inner workings) and (3) being sufficiently different from the rest (I didn't want to run variations of the same approach multiple times, as that would make the bin refinement process give them more weight by virtue of being more represented) 
A few of the tools used had a few (or many) quirks associated with them that meant that running the tool isn't able to simply run in the computing cluster as is with the input files that have been generated up to this point. I will indicate when that is the case
  5.1  Metabat2 is the first of the binning tools used. It works with a single sample at a time, and takes their corresponding contig and indexed, sorted .bam file as input to generate a depth file (SXX_depth.txt) and the corresponding bins in .fa format
  5.2  Maxbin2 is the next tool used. It also works on each sample separatedly, and uses the SXX_contigs.fasta, SXX_map_sorted.bam and the SXX_depth.txt file generated by metabat2 as its input and generates bins in .fasta format (which then necessitates renaming the files to .fa). As a perk, it presents incompatibilities with the Metabat2 and comebin modules, so it has to be ran separatedly from those two.
  5.3  Comebin is the third tool used and the last to study each sample separated from the rest. It is very guardrail-ed, so it tries to do a lot of work for the user without telling it is doing so, which actually makes the pipeline fail if not accounted for. For example, instead of accepting a sorted, indexed .bam file as input it only takes _its directory_ as input _and breaks if there are multiple .bam files within said directory_, so that means that previous to running comebin the original (unsorted, un-indexed) .bam file has to be deleted. So, it takes the SXX_contigs.fasta, the directory where SXX_map_sorted.bam resides and outputs bins in .fa format.
  5.4 Semibin is the fourth binning tool employed and the first in which multiple samples are analyzed at once. This introduces bias, as I chose to group together samples of the same type and time point (e.g., I group together S07, S08 and S09, which correspond to the soil samples at time 3), but also helps with generating bins of minoritary organisms that (suppsedly) otherwise would be missed.
  For that reason, it cannot be ran as is, but rather, necessitates generating new input files. It includes a handy tool that concatenates the input contigs into a single file while keeping track of which contig belongs to which sample which I use to generate a new, sample-type contig for each sample type (e.g., S07_contigs.fasta, S08_contigs_fasta and S09_contigs.fasta are concatenated into a new soil3_contigs.fasta). It then requires reads from all the corresponding samples to be remapped, resorted and reindexed to the new contig file (following the example, S07, S08 and S09 reads all get remapped with bowtie and resorted and reindexed with samtools to generate a soil3_map_sorted.bam file). The newly generated, multiple-sample files (soil3_contigs.fasta and soil3_map_sorted.bam) are used to train an AI model that outputs bins for each sample separatedly in .fasta format. As the last steps (training the AI model on the samples and generating bins) have to be done on a sample-per-sample basis (in our example, when doing those steps S07, S08 and S09 are treated separatedly) I run two different slurm scripts to better parallelize computing load.
  5.5 CONCOCT is the last binning tool employed. It is also studies multiple samples at a time, and is the one that requires more adaptations. Thankfully, many of them can be skipped by making use of semibin's intermediate files, such as carefully concatenating the input contig files. However, there are two peculiarities that have to be addressed for CONCOCT to work. First, it needs the .bam files to be in the cwd it is running (otherwise it just fails), so I need to move the sorted, indexed map files in .bam format into said cwd. Secondly, as it wasn't designed with a semibin tool in mind, it outputs the bins of all samples of a given type mixed together (e.g., whereas semibin outputs separated .fasta files for S07, S08 and S09, CONCOCT outputs various .fasta files in which S07, S08 and S09 bins coexist). For that reason, I wrote a python script that combs over the generated bins and generates separate bin files for the different samples that coexist within (e.g., it takes a soil3_bins.fasta file and generates the corresponding S07_bins.fasta, S08_bins.fasta and S09_bins.fasta files. It also fixes the formatting of the .fasta themselves, as CONCOCT also outputs broken fastas).
  So, CONCOCT takes the concatenated contigs fasta file generated by semibin, the sorted and indexed maps of said contigs and generates, after running the companion concoct_fix.py script, various bins in .fa format
